# Code Review та Стратегічний Аналіз проєкту "Personal Skill Monitor"

## 1. Якість коду та Архітектура

### 1.1. Порушення принципу Single Responsibility (SRP) у GUI
- **Проблема**: Клас `EVEApp` у `src/gui/app.py` виконує занадто багато функцій: ініціалізація вікна, управління макетом (layout), обробка подій, бізнес-логіка (оновлення даних) та взаємодія з API клієнтом. Це класичний "God Object".
- **Рішення**: Розділити логіку на шари. Винести бізнес-логіку (оновлення даних, управління станом) у окремий контролер або ViewModel. `EVEApp` має відповідати лише за відображення компонентів.
- **Пріоритет**: **Високий**

### 1.2. Дублювання коду та "мертвий" код
- **Проблема**: У корені проєкту знаходиться файл `esi_client.py`, який, схоже, дублює логіку з `src/core/esi.py` та `src/core/auth.py`. `main.py` використовує `src.gui.app`, тому кореневий файл виглядає як застарілий прототип.
- **Рішення**: Видалити `esi_client.py` з кореня проєкту, щоб уникнути плутанини. Перевірити, чи є в ньому унікальні функції, які варто перенести в `src/core`.
- **Пріоритет**: **Середній**

### 1.3. Відсутність типізації (Type Hinting)
- **Проблема**: У багатьох модулях (особливо в `src/gui/app.py`) відсутні анотації типів. Це ускладнює читання коду, рефакторинг та використання статичних аналізаторів (mypy).
- **Рішення**: Додати анотації типів для всіх методів та функцій. Наприклад, `def get_skills(self, char_id: int) -> dict | None:`.
- **Пріоритет**: **Середній**

### 1.4. Хардкод налаштувань UI
- **Проблема**: Кольори та стилі ("EVE Dark", "Dark") захардкоджени в `src/ui/theme_eve.py` та `src/gui/app.py`.
- **Рішення**: Винести всі константи стилів у окремий конфігураційний файл (наприклад, `theme.json` або `src/config/theme_constants.py`).
- **Пріоритет**: **Низький**

## 2. Безпека та Продуктивність

### 2.1. Блокування UI синхронними мережевими запитами (Критично)
- **Проблема**: Метод `_refresh_data` в `src/gui/app.py` викликає `self.esi_client.get_skills`, який використовує синхронну бібліотеку `requests`. Під час виконання запиту до ESI (що може тривати секунди) інтерфейс програми повністю "замерзає".
- **Рішення**: Перевести мережеві запити у фоновий потік, використовуючи `threading` або `asyncio`. Для Tkinter найкраще підійде запуск важких задач у `threading.Thread` з оновленням UI через чергу повідомлень або метод `after`.
- **Пріоритет**: **Високий** (Це основна проблема UX)

### 2.2. Зберігання токенів у відкритому вигляді
- **Проблема**: Файл `tokens.json` зберігає Refresh Tokens у відкритому вигляді. Хоча це локальний додаток, це є потенційним ризиком, якщо файл потрапить до зловмисників (наприклад, через віруси).
- **Рішення**: Використовувати системне сховище ключів (Windows Credential Manager / Gnome Keyring / KWallet) через бібліотеку `keyring`.
- **Пріоритет**: **Середній**

### 2.3. Обробка помилок
- **Проблема**: Використання загального `except Exception as e:` у багатьох місцях (наприклад, у `src/core/esi.py`). Це може приховувати логічні помилки (наприклад, `KeyError` при зміні формату API), маскуючи їх під помилки мережі.
- **Рішення**: Ловити конкретні винятки (`requests.exceptions.RequestException`, `json.JSONDecodeError`) та обробляти їх окремо.
- **Пріоритет**: **Середній**

## 3. Пропозиції для розвитку (Roadmap)

### 3.1. Нові функції

1.  **Сповіщення про завершення навичок (Desktop Notifications)**
    -   *Опис*: Відправляти системне сповіщення, коли таймер навички завершується, навіть якщо додаток згорнуто.
    -   *Технічно*: Використати бібліотеку `plyer` або нативні засоби ОС.

2.  **Імпорт плану прокачки (Skill Plan Import)**
    -   *Опис*: Можливість імпортувати план з буфера обміну (формат EVE/EVEMon) безпосередньо у чергу або план.
    -   *Технічно*: Парсинг текстового формату та співставлення назв навичок з ID через `skills_db`.

3.  **Інтеграція з ринком (Market Data)**
    -   *Опис*: Показувати орієнтовну вартість книг навичок (Skillbooks), які є у плані, але ще не вивчені.
    -   *Технічно*: Додати запит до ESI Market endpoint для отримання цін.

### 3.2. Developer Experience (DX)

-   **Впровадження Unit-тестів**: Наразі тести відсутні.
    -   *Інструмент*: `pytest`. Почати з тестування `src/core/esi.py` та парсерів, використовуючи `unittest.mock` для імітації відповідей API.
-   **Лінтери та форматери**:
    -   *Інструмент*: `ruff` (заміна flake8/isort) та `black`. Це забезпечить єдиний стиль коду та виявить прості помилки автоматично.
-   **CI/CD**:
    -   Налаштувати GitHub Actions для автоматичного запуску лінтерів та тестів при кожному Pull Request.
